## 0. Вердикт: **ВОРОТА 1→2 ПРОЙДЕНЫ, и результат противоположен задаче 23.** Пул решает исход **99 раз из 243** — но не там, где он пишет больше всего

Задача 23 закрыла тот же пул по каналу `population` вердиктом `(C)` — «не решает ни разу в 90 прогонах из 90». Здесь тот же метод, те же 90 прогонов, тот же горизонт, и результат обратный: **99 из 243 наблюдённых коллапсов (40.7 %) в теневом мире не состоялись бы**. Причина ровно та, которую постановка назвала до начала: у `population` до смерти актора был промежуточный слой (релевантность), а `cohesion` читается предикатом коллапса напрямую.

**И это не сдвиг тайминга.** В **98 случаях из 99** теневой счётчик `collapse_warning_ticks` на тике реальной смерти равен **нулю**, а в **94 из 99** теневой актор **не был в опасности ни одного тика за всю партию** (`s_dng = 0`). Разница не «умер бы на десять тиков позже», а «не подошёл бы к порогу вовсе».

### 0.1. Главный результат — не 99/243, а то, на что эти 99 приходятся

**В constantinople победа игрока — это смерть османов, и её решает пул.** Измерено в 30 прогонах scripted-базы:

- победа наступает **ровно через 3 тика** после гибели `ottomans` в **23 прогонах из 23**, где победа вообще есть (`sustained_ticks_required: 3`);
- второй конъюнкт условия победы, `actor:ottomans.military_size < 40`, истинен **ровно `300 − тик_смерти` тиков** в 23/23 и **ноль тиков** во всех семи проигранных прогонах. `military_size` османов на тике смерти — **61.7…104.7**, то есть гейт **никогда не открывается измором**: он открывается тем, что актора не стало, и `MetricRef::get` возвращает `unwrap_or(0.0)` для отсутствующего контейнера (`metric_ref.rs:219–235`);
- саму гибель османов пул решает в **19 прогонах из 23**.

Комментарий в `constantinople_1430.rs:239–242` («`ottomans.military_size` decays through combat losses (180 → ~0 by tick ~150), so `< 40` is reachable») **опровергнут измерением**, и вместе с ним — прочтение задачи 23 §14.3, где «`ottomans.military_size < 40`, тиков 97…189» было принято за достижимость гейта: эти 97…189 — целиком посмертные тики (`300 − T`). Правка не делается (объём — расследование), но пункт зафиксирован (§6, §11 п.4).

### 0.2. Три посылки постановки: две подтверждены точно, одна исправлена

1. **Предварительный скан §0.1 сошёлся по всем числам — для общего пула.** Срабатываний, пишущих `cohesion`: **44.9…73.2** за партию против объявленных «45–73». Чистый эффект общего пула: **−313.6…−457.1** против объявленных «−314…−457». Вклад `charismatic_preacher`: **+0.3…+2.4**, то есть **0.07–0.77 %** отрицательной массы, против объявленных «0.1–0.8 %». Ранжирование носителей общего пула в constantinople: `court_conspiracy` **34.9 %**, `earthquake` **34.2 %**, `flood` **26.0 %**, остальные пять — **4.9 %** вместе, против объявленных «≈35 / ≈34 / ≈26 / ~5». Совпадение построчное.
2. **Но сканом мерился только общий пул, и с учётом сценарного ранжирование меняется.** В constantinople крупнейший носитель проекта — **сценарное** событие `mehmed_threatens` (**−182.4** за партию в no-player, **28.5 %** всей отрицательной массы), а в rome сценарный пул в сумме **положителен** (**+9.6** за партию: `divine_omen +12.0` против `gladiator_revolt −2.4`). «9–12 сайтов вместо восьми» — верно, но не означает «больше стока».
3. **«Все сценарные события бьют по протагонисту» — верно про эффект и неверно про гейт.** `mehmed_threatens` нацелен на `ottomans`, гейтом стоит `ottomans.military_size > 150`, а пишет `byzantium.cohesion −8`: **актор, которого бьют, не влияет на то, сработает ли событие**. Это же и источник самого большого режимного разброса, найденного в задаче (§3.3).

### 0.3. Дефект, который стадия 1 предъявляет вместо несоответствия единиц

Вариант (A) действительно не наследуется: `cohesion` клампится в `0..100`, все акторы на одной шкале, несоответствия единиц нет — и измерение это подтверждает **сильной формой**. Размер записи и её решаемость **анти-коррелированы**: `byzantium` получает от пула **−205.2** за партию (крупнейшая запись в проекте) и не спасается **ни разу**; `wallachia` получает **−8.7** и спасается **в 10 прогонах из 10**.

Дефект другой, и он структурный: **пул решает исход ровно там, где у `cohesion` нет восстанавливающей силы**, а её отсутствие в трёх из шести случаев создано не пулом, а пропущенными ключами в конфиге спавна (§5.4, §7 (D₃)).

## 1. Инструмент и метод

Два новых режима у `budget_probe`, по образцу пары `popevents`/`decisive23` задачи 23.

**`cohevents`** — перепись срабатываний, занятости условий и разложения потока. Три вещи, которых существующие режимы выразить не могут:

1. **Занятость условия каждого события у каждого актора**, вычисленная **тем же кодом, что движок**: `cond.metric.resolve(aid)?.get(world)` и `cond.operator.evaluate(...)` (`mod.rs:485–492`). Не по виду строки в конфиге, а по значению на траектории.
2. **Занятость допуска.** У `EventTarget::Any` это `Foreground` (`mod.rs:425–431`), у `SeaActors` — ещё и тег `maritime`/`trade_empire` (`mod.rs:415–418`), у `Actor(id)` — совпадение с целью. Ни один из трёх в файлах сценариев не назван.
3. **Атрибуция записи, а не срабатывания.** Событие может сработать **на** одном акторе и записать **другому**; поэтому эффекты резолвятся через `RelativeMetricRef::resolve` и приписываются актору, который реально получил дельту. Первая версия пробника печатала строки только для актора-цели — и потеряла всю запись `mehmed_threatens`; фильтр печати исправлен, и это единственная ошибка пробника, найденная и исправленная в ходе стадии.

**`decisive24`** — контрфакт-пересчёт вердикта коллапса. Метод задачи 19 п.4 / задачи 23 §14.1, перенесён без изменений: **вторая симуляция не запускается**. Поток RNG расходится от любого изменения состояния (`interactions.rs:438` тратит четыре дополнительных броска только при успешном бою, а вероятность боя считается из метрик), поэтому её расхождения были бы неинтерпретируемы. Пересчитывается **вердикт**, тик за тиком.

Две детали, без которых счёт был бы неверен, и обе сделаны:

- **Кламп.** `cohesion` клампится дважды — при применении (`metric_ref.rs:267`, ветка `_ =>`) и ещё раз в фазе 5 (`mod.rs:705–718`). Переносимый вперёд «долг», как в задаче 23, был бы неверен в обе стороны: он кредитовал бы тень потерями, которые реальный пол уже поглотил, и позволил бы ей уйти выше 100 и не вернуться. Поэтому тень ведётся **значением со своим клампом**, продвигаемым не-событийным приращением реального мира:
  `S(t) = clamp( S(t−1) + [C(t) − C(t−1)] − δ_событий(t), 0, 100 )`.
  Долг `S − C` становится **выходом** модели, а не входом, и ограничен по построению.
- **Счётчик.** Коллапс требует **трёх подряд** опасных тиков и сбрасывается на первом неопасном (`mod.rs:1536–1552`). У тени **свой** `collapse_warning_ticks`, со своим сбросом и со своим пропуском по `minimum_survival_ticks` — ровно то, что постановка назвала обязательным.

**Где снимается вердикт, и почему это точно, а не в первом приближении.** `check_collapses` — фаза 7. После неё `cohesion`, `legitimacy`, `external_pressure` и `military_size` не пишет никто: `phase_vassalage` пишет только `expansion_count`, `phase_record` — только `family_state`, `phase_advance` — только часы. Значит метрики, наблюдаемые **после** возврата из `tick()`, — ровно те, которые прочла фаза 7. Актор, погибший в этом же тике, уже удалён из `world.actors`, но его метрики на момент вердикта сохранены в `dead_actors[].final_metrics` (`mod.rs:1578`), откуда и берутся.

**Репликация проверена, а не объявлена.** Реплицированный **реальный** счётчик сверяется с `world.collapse_warning_ticks` каждый тик у каждого актора: `cw_mismatch = 0` в **90 прогонах из 90** (≈ 315 тысяч актор-тиков). Это и есть доказательство, что теневой счётчик считает то же, что движок, только на других значениях.

**Прочее.** `scripted_step` и `assert_pool_matches_source` переиспользованы; добавлен `assert_pool_matches_metric`, который валит прогон, если `common_events()` перестал совпадать с объявленными восемью писателями `cohesion` и шестью — `economic_output`. Репликация scripted сверена с `sim` заново: `sim constantinople_1430 300 scripted balanced 42` → тик победы **165** = `#POOL` пробника; `sim milan_1477 300 scripted aggressive 42` → **22** применения `milan_raise_troops` = `#POOL` пробника. Движок и контент **не тронуты** ⇒ `sim` байт-в-байт по дифу.

**Что мерялось:** 10 калибровочных сидов `42,1,7,13,99,3,21,55,77,88`, горизонт 300 тиков. `cohevents` — три сценария × (no-player + одна scripted-стратегия). `decisive24` — три сценария × (no-player + все сценарные стратегии: constantinople `balanced`/`military`/`diplomacy`, rome `balanced`/`wealth`, milan `aggressive`) = **90 партий**, **315 518 актор-тиков** и 1220 актор-партий — те же числа, что в задаче 23 §14.1. Все числа ниже — на партию, среднее по 10 сидам, если не сказано иное.

## 3. Шаг 2 — вырожденность условий, оба режима

Занятость — доля тиков жизни актора, %, среднее по 10 сидам, по акторам, для которых событие вообще допустимо.

### 3.1. Гейт допуска `Foreground` — перемерен, а не процитирован

| сценарий | режим | минимум | медиана | максимум |
|---|---|---|---|---|

### 3.2. Второй гейт допуска, которого в задаче 23 не было: `SeaActors`

**Прямое следствие для §1 п.3 постановки: «суммарный чистый эффект против вклада остальных писателей» на насыщенном акторе — величина без смысла.** У потолка не-пуловые писатели доставляют не то, что стоит в конфиге, а ровно столько, чтобы вернуть 100. Разложение потока поэтому приводится только для акторов, у которых `coh = 100 %` близко к нулю (§4.4), а для остальных вместо него приводится занятость границы.

### 5.6. Канал `economic_output`: у него нет ребра в предикат коллапса, и это установлено обходом

Ни одно из четырёх правил, пишущих `cohesion`, не читает `economic_output` (§2.1). Прямого пути от `eo` к смерти нет. Достижимые каналы — те же два, что строила задача 23: релевантность (обе метрики среди восьми — учтено в §5.5) и казна через `income = eo · pop · 0.001`.

**Теневая казна измерена, но её результат объявляется недостоверным, и причина называется здесь, а не в примечании.** Модель тени «вычесть записанную дельту» неверна для **положительного** писателя у потолка: `trade_boom +5` при `eo = 100` реально усекается клампом и не доставляет ничего, а тень вычитает все 5. `trade_boom` тождественно истинен 84–99.4 % (§3.3), `eo` стоит у потолка 72–94 % (§4.3) — значит ошибка систематическая и большая. Она видна по знаку: `treas_debt` выходит **отрицательным** (−1343 … −59 304 за партию), то есть модель утверждает, что без событий казна была бы **меньше**, при том что чистый эффект пула на `eo` отрицателен (−214.8 … −407.9).

У `cohesion` этой ошибки нет и это проверено, а не предположено: положительных записей у потолка за 60 партий **одна** (`clip_hi = 1`, rome / no-player) — `charismatic_preacher` по построению гейта (`coh < 40`) у потолка невозможен, а `divine_omen` бьёт по `rome`, который у потолка 0.1–4.6 % времени.

**Вывод по `eo` формулируется в том виде, в каком он обоснован:** даже под завышенным на порядки долгом расхождение гейтов доступности действий равно **0** в семи конфигурациях из девяти, **1** в constantinople `balanced` и **5** в `diplomacy`. Исключение — milan `aggressive`, `gate_div = 965`, и это **тот же артефакт первого порядка, который задача 23 §14.3 уже разобрала**: сценарная дисциплина milan тратит казну до порога `raise_troops = 70` каждый тик, поэтому любой ненулевой долг переворачивает вердикт гейта независимо от величины. Канал `eo → казна → победа` этой стадией **не закрыт**; он объявлен неизмеренным (§12).

## 7. Шаг 5 — развилка: **сформулирована, не выбрана**

### (A) Нормировка по запасу — **неприменима, и это подтверждено, а не унаследовано**

`cohesion` и `economic_output` клампятся в `0..100`, все акторы на одной шкале — несоответствия единиц нет по построению. Измерение подтверждает это в сильной форме: цена одного попадания в долях «запаса» тождественна для всех акторов, а решаемость с размером записи **анти-коррелирована** (§0.3, §4.4). Вариант закрыт.

### (B) Исключение акторов или условий

Форма: поставить гейт, не пускающий безусловные события (`earthquake`, `flood`, `court_conspiracy`) туда, где актор уже у нижней границы, — например, порог `cohesion > 15` на отрицательные записи, или исключение только что заспавненных акторов.

**Арифметика до кода.** Разрыв по когезии на тике смерти — 6…86 пунктов, медиана ≈ 20; средняя запись пула у решающих акторов — 8.2…35.7 за партию при 45–73 срабатываниях по сценарию. Любой порог, который спасает `wallachia` (−8.7 за партию, гибнет 10/10), спасает и `ottomans` (−16.4, гибнет 10/10) — а это **та самая смерть, которой куплена победа** (§6). Интервал «спасти спавны, не спасая османов» **пуст**: `wallachia` получает меньше, чем `ottomans`, поэтому порог, отсекающий первую, отсекает и вторых. Вариант не закрыт полностью, но требует отдельного обоснования, почему исход constantinople должен измениться.

### (C) Признать намеренным

По стандарту задачи 19 п.4 и задачи 23 §14 — подтверждать измерением, а не отсутствием дешёвой правки. Материал в обе стороны:

- **за (C):** пул — **не** главный сток ни у кого (§4.4), пороги коллапса жёсткие, и «маргинальный вклад решает» — свойство любой пороговой механики, а не дефект. Задачи 7/8 (`combat-guard-mortality-coupling`) уже показали, что смертность в этом движке держится на одном канале и что её выключение — не побочный эффект, а результат: `cohesion` из пула сегодня несёт **78 %** смертности на двух путях из трёх. Убрать её — повторить тот же дефект другим способом.
- **против (C):** 63 из 99 решающих случаев (64 %) созданы **пропущенными ключами в трёх `spawn_actor`** (§5.4) — то есть механика держится на конфигурационном упущении, а не на замысле; и достижимость победы constantinople держится на том, что смерть актора читается как `military_size = 0.0` через `unwrap_or` (§6), что тоже трудно назвать замыслом.

**Стадия 1 (C) не закрывает.** В отличие от задачи 23, где `(C)` доказывался нулём, здесь он упирается в вопрос замысла, и вопрос вынесен постановщику (§11 п.2).

### (D) Найденное при обходе — четыре кандидата, ни один не выбран

- **(D₁) Три спавна constantinople без `external_pressure`.** 63 из 99 решающих случаев. Дописать ключ — правка одной строки в `milestone_events.toml` ×3, но она **перекалибрует** сценарий: `Bonus`-правило начнёт давать этим акторам до +3.5/тик. Это тот же класс, что «фантомный сток на спавнах» из очереди «за скобками», и его надо решать там, а не здесь.
- **(D₂) Гейт, не стоящий на жертве.** `mehmed_threatens` гейтуется `ottomans.military_size > 150`, нацелен на `ottomans`, а пишет `byzantium.cohesion −8`. Актор, которого бьют, не влияет на то, случится ли удар. Отсюда же и рекордный режимный разброс 228 → 35 срабатываний.
- **(D₃) `cohesion_natural_decay` отсутствует у constantinople.** Единственная причина, по которой девять акторов сценария проводят у потолка 46–87 % партии и структурно иммунны к пулу, а три спавна — нет. Асимметрия контента, не событий.
- **(D₄) Наследник рождается на `cohesion = 20`** (К-2, `mod.rs:1645`), в пяти пунктах от `internal_collapse`, независимо от состояния родителя. Единственная причина, по которой `ostrogoth_kingdom` (15 из 99) вообще попадает в зону.

**Отдельно — три мёртвых сайта, найденных обходом и не входящих в развилку:** `barbarian_raid` и `army_mutiny` (rome) не срабатывают **ни разу за 30 партий** (гейт 0.0 %); `piracy` структурно недостижим в rome (ноль морских акторов). Это долг того же класса, что «девятый сайт» задачи 13, и здесь только фиксируется.

### 8.2. Общее для всех вариантов, сказанное до прогона

**Поток RNG расходится при любом изменении величины** (`interactions.rs:438`), поэтому побайтовое сравнение траекторий невозможно — это установлено задачей 22 эмпирически и задачей 23 заранее, и здесь повторяется без изменений.

**Специфическое для этой задачи и более жёсткое:** канал ведёт к смерти актора, а состав мира — вход почти всего остального (соседи, бой, миграция, `EventTarget::Any`). Поэтому здесь расходится не «часть чисел», а **вся сводка сразу**, и это надо принять как цену, а не как признак ошибки.

### 8.3. Что объявляется допустимым сдвигом (до первого прогона стадии 2)

1. **Constantinople — здесь цель и здесь же главный риск, и границы поэтому асимметричны.** Правка адресована трём спавнам и/или безусловным событиям; но по §6 она напрямую бьёт по достижимости победы. Объявляется: доля побед **не ниже 21/30**, медиана тика победы **151 ± 25**, гибель `byzantium` до победы **не чаще 8/30**. **Дополнительно и обязательно:** доля прогонов, в которых `ottomans` гибнут, **не ниже 20/30** (база 23/30) — без этой строки правка может остаться зелёной по трём предыдущим и при этом сменить механизм победы, ровно так, как провалилась стадия 2 задачи 20.
2. **Rome — охраняется жёстко:** смен поколений **ровно 4** в 10/10, тик победы `balanced` **31** в тех же **7** сидах. Rome даёт 17 из 99 решающих случаев, то есть правка там работает, но дуга протагониста от неё не зависит (`rome` у потолка 0.1–4.6 %, пул даёт ему −35.9 при росте когезии).
3. **Milan — обязан не сдвинуться вовсе по исходу:** `milan_raise_troops` **±10 %** от 200, `italy_unified` достижим **10/10**, медиана тика **±10** от 82. Основание: milan даёт **ноль** решающих случаев, все 42 его смерти идут по `conquest_collapse`. Если milan сдвинется по составу мира — правка вышла за объём.
4. **Критерий, специфичный для этой задачи, и он же отличает починку от выключения механики.** Судить надо не по числу коллапсов и не по массе записи, а по **доле смертности, приходящейся на два пути, читающих `cohesion`**. База: **127 из 243 (52.3 %)**, из них решено пулом **99 (78 %)**. Правка, после которой эта доля падает ниже **35 %**, выключила механику смертности, а не починила единицы — и это тот же исход, которым закончились задачи 7/8, где «починка» фантомного боя молча убила всю смертность. Порог выведен, а не выбран: 35 % — это уровень, ниже которого `conquest_collapse` становится единственным работающим путём (сегодня он даёт 47.7 %).

## 14. Воспроизведение

```bash
SEEDS=42,1,7,13,99,3,21,55,77,88

# полный обход контейнеров (перепись всех ключей печатается до фильтра)
cargo run --release --bin budget_probe -- inventory cohesion
cargo run --release --bin budget_probe -- inventory economic_output

# срабатывания, занятость условий и допуска, разложение потока — оба режима
for sc in constantinople_1430 rome_375 milan_1477; do
  cargo run --release --bin budget_probe -- cohevents $sc 300 $SEEDS noplayer; done
cargo run --release --bin budget_probe -- cohevents constantinople_1430 300 $SEEDS balanced
cargo run --release --bin budget_probe -- cohevents rome_375 300 $SEEDS balanced
cargo run --release --bin budget_probe -- cohevents milan_1477 300 $SEEDS aggressive

# контрфакт вердикта коллапса — 90 партий
for sc in constantinople_1430 rome_375 milan_1477; do
  cargo run --release --bin budget_probe -- decisive24 $sc 300 $SEEDS noplayer; done
for st in balanced military diplomacy; do
  cargo run --release --bin budget_probe -- decisive24 constantinople_1430 300 $SEEDS $st; done
for st in balanced wealth; do
  cargo run --release --bin budget_probe -- decisive24 rome_375 300 $SEEDS $st; done
cargo run --release --bin budget_probe -- decisive24 milan_1477 300 $SEEDS aggressive

# база §8.1
for st in balanced military diplomacy; do
  cargo run --release --bin budget_probe -- attractor constantinople_1430 300 $SEEDS $st; done
cargo run --release --bin budget_probe -- attractor rome_375 200 $SEEDS balanced
cargo run --release --bin budget_probe -- attractor milan_1477 300 $SEEDS aggressive

# сверка репликации с sim
cargo run --release --bin sim -- constantinople_1430 300 scripted balanced 42   # тик победы 165
cargo run --release --bin sim -- milan_1477 300 scripted aggressive 42          # raise_troops 22
```

Решающие столбцы: `#CF24` — `saved` (сколько коллапсов не состоялось бы), `saved_pool` (то же для общего пула отдельно), `cw_mismatch` (сверка репликации, обязан быть 0); `#DEATH` — построчный разбор каждой смерти с путём, обоими счётчиками и обеими когезиями; `#GATE` — занятость условия и допуска по каждому событию и актору.

**Оговорка о среде** (та же, что §13.1 задачи 22 и §13 задачи 23): на хосте (SteamOS) нет `cc`/`gcc` и dev-пакетов `webkit2gtk-4.1`, которых требует `tauri 2`, поэтому все сборки сделаны в контейнере `distrobox dev` (Ubuntu 22.04, `libwebkit2gtk-4.1-dev`).
