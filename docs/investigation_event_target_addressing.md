## 0. Вердикт: **ВОРОТА 1→2 ПРОЙДЕНЫ.** `(D₂)` уникален — 1 событие из 46 — но по каналу коллапса он снимает **ноль** и добавляет **25 смертей, все `ottomans`**

Постановка требовала установить три вещи до кода: уникален ли дефект, что даёт каждый вариант адресации числом, и не пересекается ли он с `(D₁)`. Все три получены измерением.

1. **Уникальность — да, и она посчитана, а не увидена.** Полный обход четырёх контейнеров событий проекта (46 событий): у **одного** пересечение цели и адресатов эффектов пусто — `mehmed_threatens`. Ещё у **одного** гейт читает другого актора — `barbarian_raid` (rome), и это ровно зеркало: гейт на чужом акторе, эффекты на своей цели. Оба — единственные в своём классе, и оба патологичны, но по-разному (§3).
2. **Цена по каналу коллапса — асимметрична, и это главный результат.** Вариант `(i)` (перенос записи когезии на актора гейта) снимает **0 из 102** решающих коллапсов и **добавляет 25**, все на `ottomans`, все по пути `classic_collapse`: **17 смертей новых** (в реальном прогоне актор не погибал вовсе) и **8 тех же смертей на 8–26 тиков раньше**. Вариант `(i′)` даёт те же 25 добавленных и вдобавок снимает **13** — все `byzantium`, потому что вместе с когезией уносит с него `external_pressure +10`.
3. **Пересечение с `(D₁)` — прямое ноль, косвенное `+1.65 %`.** Ни один из трёх спавнов не сдвигается ни в одном варианте (103 актор-прогона, 0 расхождений): `mehmed_threatens` им ничего не пишет. Косвенный канал — разбавление жребия `EventTarget::Any` из-за более ранней гибели `ottomans` — посчитан огибающей и составляет **+8 бросков на 40 партий** против нынешних 486, то есть **+1.65 %** и в сторону ухудшения (§6).

### 0.1. Что найдено сверх постановки — четыре расхождения, все от измерения

1. **Эффектов у события три, и третий бьёт по условию победы напрямую.** Постановка это назвала (`global:federation_progress +5`), но не знала главного: **глобальные метрики клампятся в `0..100`** (`metric_ref.rs:279–287`), и `federation_progress` в scripted-режимах **упирается в потолок 100 к тику 4–12**. Номинальный вклад пула в `fed` — `+188…+203` за партию против отрицательных `−196…−226`; реализуется **`+97…+98`**, потерь на клампе **92…136 за партию**. Гипотеза постановки «+114 в no-player против +17.5 в scripted» **подтверждена по форме и исправлена по числам**: `+115.0` (no-player), `+12.0` (balanced), `+13.0` (military), **`+88.0` (diplomacy)** — то есть режимный разброс не 6.5×, а **9.6×**, и diplomacy ведёт себя как no-player, а не как balanced.
2. **Риск, ради которого вводился критерий №2, измерением снят.** Опасение «`(i)` убьёт `ottomans` раньше, чем `fed` дойдёт до 80» **не подтверждается**: в scripted `fed ≥ 80` наступает на тиках **4–12**, а теневые смерти `ottomans` — на тиках **103–232**. Ни одного случая «смерть без победы» вариант не создаёт.
3. **Зато `(i)` меняет механизм победы способом, которого ни один объявленный критерий не ловит.** Предсказание на теневых числах: победы **22/30 → 29/30**, медиана **145.5 → 152** (в объявленной полосе), гибель `byzantium` до победы **8/30 → 8/30**, «гибель `ottomans` без победы» **0/30 → 0/30**, доля когезионных путей **52.8 % → 55.8 %**. Все шесть критериев проходят. **Но все 7 добавленных побед — в прогонах, где протагонист уже мёртв**: побед при живом `byzantium` **22/30 → 22/30**. Недостающий критерий назван в §10.3.
4. **Довод против `(i′)` из постановки подтверждён числом, и он больше, чем ожидалось.** Перенос `external_pressure +10` с `byzantium` тушит гейт `greek_scholars_flee` (`byz.ep > 70`): занятость **99.0 % → 64.8 %** (balanced), **97.4 % → 22.2 %** (diplomacy), **93.4 % → 57.7 %** (no-player); вердикт гейта расходится на **1027 / 852 / 163** тиках. То есть `(i′)` — это правка двух событий, из которых второе в ней не названо.

## 1. Инструмент и метод

Два новых режима `budget_probe`. Режимы `popsink`/`decisive` (задача 21), `popevents`/`decisive23` (задача 23), `cohevents`/`decisive24` (задача 24), `spawnwalk`/`decisive25`/`poolcut` (задача 25) переиспользованы **без единого изменения** — проверено: `git diff -- src/bin/budget_probe.rs | grep -c '^-[^-]'` = **0** удалённых строк, диф — только вставки.

**`evaddr`** — обход адресации. Печатает по каждому событию каждого из четырёх контейнеров (`common_events()` + три `create_random_events()`): цель и её тип, число ключей эффектов и условий по пяти классам адресации, флаги «пересечение цели и адресатов эффектов пусто» и «гейт читает другого актора», и поимённо — кого именно называют чужие ключи. **Классификация делается через `RelativeMetricRef::resolve`, то есть тем же вызовом, что движок** (`mod.rs:485` и `:492`), а не разбором вида строки: ключ, который выглядит абсолютным, но называет цель, попадает в класс «адресован цели», как и `self.<metric>`.

**`evtarget`** — измерение и контрфакт. Рядом с реальным прогоном ведутся **четыре** теневых значения когезии на каждого актора (по одному на вариант) и одно теневое `external_pressure` (для `(i′)`), каждое со своим клампом и своим `collapse_warning_ticks`, своим сбросом и своим пропуском по `minimum_survival_ticks`. **Вторая симуляция не запускается** — запрет §7.5 постановки; довод тот же, что в задачах 23–25: поток RNG расходится от любого изменения состояния (`interactions.rs:438`).

Тень здесь **дифференциальная**, а не полная реплика (в отличие от `decisive25`): `byzantium` и `ottomans` участвуют во всех взаимодействиях, и воспроизвести их траекторию целиком пробник не может. Поэтому ведётся
`S_v(t) = clamp( S_v(t−1) + [C(t) − C(t−1)] + δ_v(t), 0, 100 )`,
где `δ_v(t) = (что вариант v записал бы) − (что записал прогон)`. Для `Cut` это `−ev(t)`, то есть в точности тень задачи 24; для `(i)` — `+8` `byzantium` и `−8` `ottomans` на каждое срабатывание.

**Два собственных теста режима, оба обязательные и оба пройдены:**

| тест | что обязан дать | дал |
|---|---|---|
| **пол**: вариант `Base` (адресация не изменена) | тень тождественна реальному миру ⇒ `saved = 0`, `added = 0` | **0 / 0** в 90 партиях |
| **эквивалентность**: вариант `Cut` (снять все записи событий в `cohesion`) | воспроизвести `decisive24` точно | **102 = 102**, коллапсов **248 = 248**, `cw_mismatch = 0` |

Второй тест — то же по смыслу, что тест `α = 1` у `poolcut` задачи 25: новый режим обязан уметь воспроизвести опубликованный. Он воспроизводит его на всех девяти конфигурациях по отдельности, а не только в сумме (§5.1).

**Репликация реального счётчика проверена, а не объявлена:** реплицированный `collapse_warning_ticks` сверяется с `world.collapse_warning_ticks` каждый тик у каждого актора — **`cw_mismatch = 0` в 90 прогонах из 90**.

**Репликация scripted сверена с `sim` заново:** `sim constantinople_1430 300 scripted balanced 42` → тик победы **165** (совпадает с `#FED victory=165` пробника); `sim milan_1477 300 scripted aggressive 42` → **`milan_raise_troops: 22`**. Движок и контент не тронуты ⇒ `sim` байт-в-байт по дифу.

**Что мерялось.** 10 калибровочных сидов `42,1,7,13,99,3,21,55,77,88`, горизонт 300 тиков, три сценария × все сценарные стратегии + no-player = **90 партий, 248 коллапсов** — те же числа, что у задач 23/24/25. Все величины «за партию» — среднее по 10 сидам, если не сказано иное.

## 2. Шаг 1 — семантика трёх слотов, по коду вызывающего

`phase_random_events` (`mod.rs:396–520`), построчно:

| слот | код | что делает на самом деле |
|---|---|---|
| `target` | `mod.rs:452–470` | **допуск и атрибуция.** Для `EventTarget::Actor(id)` условие ровно одно: `world.actors.contains_key(id) && !dead_actor_ids.contains(id)`. **`Foreground` здесь не участвует** — он входит только в `Any`/`SeaActors`/`All` (`mod.rs:421–431`). Выбранный `target_id` уходит в `Event::new(... target_id ...)` (`mod.rs:497`), то есть определяет, про кого событие в летописи |
| `conditions` | `mod.rs:479–487` | **частота.** `cond.metric.resolve(target_id)` — но `resolve` привязывает к цели **только** форму `self.<metric>` (`metric_ref.rs:404–413`); любой другой ключ — `Absolute` и цель игнорирует |
| `effects` | `mod.rs:489–494` | **запись.** Тот же `resolve`, та же дихотомия. Запись в отсутствующего актора молча теряется (`metric_ref.rs:259`, `if let Some(actor)`) |

**Движок предлагает форму, которая привязывает ключ к цели, и сценарии constantinople ею не пользуются ни разу.** По обходу: `self.`-ключей в проекте **37**, все — в общем пуле; абсолютных актор-ключей **83**, все — в сценарных событиях. То есть общий пул адресуется относительно цели по построению, а сценарный — поимённо, и вопрос «совпадает ли адресат с целью» для него вообще может быть задан.

**Гаснет ли `mehmed_threatens` после гибели `ottomans` — по допуску, по гейту, или по обоим: по обоим, и это измерено, а не выведено.** Допуск: цели нет в `world.actors` ⇒ `target_ids` пуст. Гейт: `MetricRef::get` возвращает `unwrap_or(0.0)` для отсутствующего контейнера (`metric_ref.rs:219–235`) ⇒ `0 > 150` ложно. Измерение: **`gate_true == gate_true_alive` во всех четырёх режимах** (2960/2960, 447/447, 344/344, 2349/2349) — за 40 партий **ни одного тика**, на котором гейт был бы истинен при мёртвом акторе. Одного из двух механизмов достаточно, и предварительная оценка постановки («после гибели `ottomans` событие остаётся мёртвым и так») **подтверждена**.

## 3. Шаг 2 — полный обход адресации: 46 событий, две аномалии, обе единичные

| контейнер | событий | `self.`-ключей | абсолютных актор-ключей |
|---|---|---|---|
| `common_events()` | 11 | 37 | 0 |
| `constantinople_1430` | 8 | 0 | 17 |
| `rome_375` | 8 | 0 | 15 |
| `milan_1477` | 19 | 0 | 51 |
| **всего** | **46** | **37** | **83** |

**Итог обхода — две строки:**

```
#ADDRSUM  events=46  empty_isect=1  gate_other_actor=1  both=0
#ADDRFLAG constantinople_1430 mehmed_threatens  empty_isect=1 gate_other_actor=0 target=ottomans other_actors=byzantium
#ADDRFLAG rome_375           barbarian_raid    empty_isect=0 gate_other_actor=1 target=rome     conds_on_other_actors=visigoths.military_size>80
```

**Формулировка `(D₂)` уточняется измерением, и уточнение существенно.** Постановка (§7.1) уже отвергла прочтение «эффект адресован не цели» как идиому; обход показывает, что идиома — именно она: `crusade_call` пишет `hungary.military_size`, `ottoman_spy_caught` — `ottomans.external_pressure`, `italian_league_against_milan` — пятерым чужим акторам сразу. Уникально у `mehmed_threatens` другое: **его цель не получает ничего**. И его гейт при этом стоит **на цели** (`cond_same = 1`) — то есть неверна и формулировка «гейт не на жертве»: гейт на цели, мимо цели идут **эффекты**.

**Зеркальный случай, найденный тем же обходом и не входивший в постановку.** `barbarian_raid` (rome): цель `rome`, эффекты все на `rome`, гейт — `actor:visigoths.military_size > 80`. Задача 24 §3.3 измерила его как мёртвый (0 срабатываний за 30 партий, занятость 0.0 %) и записала в «мёртвые сайты» без причины. Причина здесь: `visigoths.military_size` стартует с **48.0** (`rome_375.rs:404`) при пороге **80**, а расти ему в rome не от чего. То есть класс «гейт на третьем акторе» в проекте представлен **двумя** событиями, и оба вырождены — одно в тождественно-истинную сторону (98.7 % занятости у `mehmed_threatens` в no-player), другое в тождественно-ложную.

**Третий флаг обхода снят как ложный:** `senator_bribe` (rome) гейтуется `family:wealth > 200`. Первая версия классификатора считала это «гейтом не на цели»; исправлено — семейная и глобальная область не есть «другой актор», и это отдельный класс. Ошибка найдена и исправлена внутри стадии, числа §3 сняты после исправления.

## 6. Шаг 5 — пересечение с `(D₁)`: прямое ноль, косвенное `+1.65 %`

**Прямое.** `mehmed_threatens` не пишет ни одному из трёх спавнов, поэтому их теневые значения тождественны реальным во всех вариантах. Измерено, а не выведено: **103 актор-прогона трёх спавнов, 0 с ненулевым `saved`/`added`** в `(i)` и `(i′)`.

### 10.3. Критерий, которого не хватает, и он выводится, а не выбирается

Шесть порогов §7.7 — односторонние, и `(i)` двигает каждый в «хорошую» сторону. При этом он меняет механизм: **7 из 29 побед достаются миру, где протагонист мёртв 130–200 тиков.** Существующий критерий «гибель `byzantium` до победы ≤ 8/30» этого не ловит, потому что в базе те же 7 прогонов уже учтены как «`byzantium` погиб, победы нет» — числитель не меняется, меняется смысл.

**Предлагается к ратификации:** **доля побед при живом `byzantium` на тике победы — не ниже 20/30** (база **22/30**; у `(i)` предсказано **22/30**, то есть критерий проходит и в этом варианте, но начинает следить за тем, за чем шесть остальных не следят). Порог выведен так же, как «≥20/30» для гибели `ottomans`: база минус два прогона, то есть допуск на переброс RNG, а не на смену механизма.

Без этого критерия любая правка, увеличивающая смертность `ottomans`, проходит приёмку целиком — включая правку, после которой сценарий выигрывается сам собой при мёртвом протагонисте.

## 12. Что требуется от постановщика до стадии 2

1. **Решить `(D₂)`-0.** Измеримая часть закрыта в обе стороны: аномалия уникальна (1 из 46), цена по каналу коллапса — **ноль**. Остаётся вопрос замысла: считается ли дефектом то, что единственное событие проекта не даёт узнать из своей цели, кого оно ранит. **Если ответ «намеренно» — правильный адрес правки не сценарий, а правило валидатора задачи 1** («событие, ни один эффект которого не адресован его цели»), и тогда задача 24 закрывается без изменения баланса.
2. **Выбрать вариант — или отклонить все.** Числа §8 не выделяют «дешёвого» варианта: `(i)` меняет исход сценария (22/30 → 29/30) при нулевой пользе для того, ради чего задача 24 заводилась (0 из 102); `(i′)` вдобавок молча правит второе событие; `(ii)` создаёт две аномалии вместо одной; `(iii)` вычитает 78–86 % срабатываний. Вариант «ничего не менять в балансе, починить конвенцию» (п.1) на этих числах выглядит сильнее любого из четырёх — но это решение постановщика, не стадии 1.
3. **Ратифицировать или отклонить критерий §10.3** (доля побед при живом `byzantium` не ниже 20/30). Без него приёмку проходит правка, после которой сценарий выигрывается при мёртвом протагонисте.
4. **Принять к сведению три факта вне объёма:**
   (а) **глобальные метрики клампятся `0..100`** — `federation_progress` насыщается к тику 4–12 в scripted, и «накопление до 80» как модель победы неверно; это касается и формулировок задачи 24 §6, и всякой будущей работы с глобальными метриками;
   (б) `barbarian_raid` (rome) мёртв **по установленной причине**: гейт `visigoths.military_size > 80` при стартовых **48.0** — задача 24 фиксировала факт без причины, теперь причина есть; это единственное в проекте событие с гейтом на третьем акторе;
   (в) `byzantium` в no-player и diplomacy гибнет **отчасти из-за `mehmed_threatens`**, но через `external_pressure`, а не через `cohesion`: 13 из его смертей снимаются вариантом `(i′)`.

## 15. Воспроизведение

```bash
SEEDS=42,1,7,13,99,3,21,55,77,88

# обход адресации: 46 событий, четыре контейнера
cargo run --release --bin budget_probe -- evaddr

# каналы, тень с переадресацией, огибающие — 90 партий
for sc in constantinople_1430 rome_375 milan_1477; do
  cargo run --release --bin budget_probe -- evtarget $sc 300 $SEEDS noplayer; done
for st in balanced military diplomacy; do
  cargo run --release --bin budget_probe -- evtarget constantinople_1430 300 $SEEDS $st; done
for st in balanced wealth; do
  cargo run --release --bin budget_probe -- evtarget rome_375 300 $SEEDS $st; done
cargo run --release --bin budget_probe -- evtarget milan_1477 300 $SEEDS aggressive

# самотест эквивалентности: колонка saved_cut обязана совпасть с saved у decisive24
for st in noplayer balanced military diplomacy; do
  cargo run --release --bin budget_probe -- decisive24 constantinople_1430 300 $SEEDS $st; done

# разложение потока когезии (режим задачи 24, без изменений)
cargo run --release --bin budget_probe -- cohevents constantinople_1430 300 $SEEDS
cargo run --release --bin budget_probe -- cohevents constantinople_1430 300 $SEEDS balanced

# охраняемая база §9
for st in balanced military diplomacy; do
  cargo run --release --bin budget_probe -- attractor constantinople_1430 300 $SEEDS $st; done
cargo run --release --bin budget_probe -- attractor rome_375 200 $SEEDS balanced
cargo run --release --bin budget_probe -- attractor milan_1477 300 $SEEDS aggressive

# сверка репликации с sim
cargo run --release --bin sim -- constantinople_1430 300 scripted balanced 42   # тик победы 165
cargo run --release --bin sim -- milan_1477 300 scripted aggressive 42          # raise_troops 22
```

Решающие столбцы: `#ADDRSUM` — `empty_isect` и `gate_other_actor` (обход); `#ET` — `saved_*` / `added_*` по вариантам и `cw_mismatch`; `#ADD` — каждая добавленная смерть с обоими тиками, классом (`new`/`earlier`) и путём; `#FED` / `#FEDW` — реализация против номинала и доли писателей; `#ENV` — допуск, гейты и занятость чужого гейта в тени; `#II` — семейство кандидатов для `(ii)`.

**Оговорка о среде** (та же, что §13 задач 22–25): на хосте (SteamOS) нет `cc`/`gcc` и dev-пакетов `webkit2gtk-4.1`, которых требует `tauri 2`, поэтому все сборки сделаны в контейнере `distrobox dev` (Ubuntu 22.04, `libwebkit2gtk-4.1-dev`).
