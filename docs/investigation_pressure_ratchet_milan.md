# Задача 27, заход `(B)` для `milan_1477` — храповик `external_pressure`: перепись производителей, равновесный расчёт, развилка

Отдельный заход, объявленный §13.2 и итоговым статусом constantinople-захода: «`(B)` для **milan** (производитель — миграционный перенос, `2324` за партию, `46` смертей `conquest`) — отдельный нерешённый заход со своим равновесным расчётом». Метод constantinople-захода переносится, ответы — нет.

## 0. Вердикт

**Правки нет. Развилка решена в пользу `(C)` — с формулировкой, отличной от constantinople.** Плюс один найденный при обходе объект `(D)`, который крупнее всего, что задача 27 до сих пор мерила, и одно измерение, которое **не воспроизводит число, на котором был отклонён `(A)`** и потому выносится постановщику.

Пять чисел, все получены до выбора и все — этим прогоном:

1. **Адрес, ради которого заход заводился, опровергнут.** Миграционный перенос в milan — `2 608…2 670` за партию (подтверждает `2324` задачи 26 с поправкой на `(A₁)+(A₂)`), но он **не несущий**: его полное удаление снимает **`0` из `46`** смертей `conquest` сценария. Не «мало», а ровно ноль.
2. **И ни один другой производитель тоже.** Удаление тегов целиком — `0`. Удаление всех четырёх `auto_deltas` — `0`. Удаление боя — `0`. Причина не в силе правки: `external_pressure` в milan **переснабжён в `8.3…41.5` раза** (медиана ≈ `24×`). Четыре производителя избыточны: боя **одного** хватает на `35` смертей из `46`, миграции **одной** — на `31` из `46`.
3. **Найден производитель, которого не считал никто, и он больше всех остальных вместе.** `apply_actor_tags` (`mod.rs:684`) переприменяет `metrics_modifier` каждого тега **каждый тик**. В milan это `71 %` всего притока (`10 263…10 483` за партию), в rome — `93 %`, в constantinople — `59…75 %`. Два из трёх `ep`-тегов milan **заразны**: `ottoman_frontier` доходит до **всех 14** акторов, `french_orbit` — до **13** (кроме `sicily`), и у двенадцати из четырнадцати это происходит к тику `1…18` (среднее по сидам). Стадия 1 задачи 27 не видела этот канал вовсе: он падал в остаток, который она называла боем.
4. **Довод «против `(C)`» в milan исчезает сильнее, чем в constantinople.** Полоса вассалитета — `0` актор-тиков из `314 026` (число constantinople-захода воспроизведено **другим инструментом** до единицы). Все четыре контентных читателя порога milan истинны `94.8…99.7 %` тиков — включая **веху** `otranto_falls` (`ep > 80`), которая срабатывает почти так же часто, как `otranto_threat_rises` (`ep > 60`). Миграционный гейт: `87.7…89.4 %` срабатываний с источником на потолке, средняя «шкала» `32.4…33.2` из `35`.
5. **`(A)`, перемеренный для milan честно, ведёт себя не так, как записано.** Свип затухания на номинальной модели: `λ ≤ 2` снимает **`0`** смертей во всех девяти конфигурациях; `λ = 4` — `conquest` `120 → 54` (**критерий `≥ 42` пройден**), в milan `46 → 8`; `λ = 8` — `120 → 1`. Утверждение стадии 1 «затухание снимает все `120` из `120` при любом `λ ≥ 0.25`» этим инструментом **не воспроизводится**. Заход `(A)` не переоткрывает — он это фиксирует и передаёт постановщику (§9).

**`(C)` в формулировке milan:** не «у храповика нет достижимого потребителя» (это constantinople), а **у храповика нет единственного производителя**. Метрика насыщается к тику `7.5…17.7` четырьмя независимыми каналами, каждый из которых почти самодостаточен, а два самых крупных — движковые и исключены из объёма явно (бой — §8.8 constantinople-захода; тег-канал — общий для трёх сценариев). Правка «производителя» здесь не имеет объекта, а не имеет эффекта.

## 1. Инструмент: почему прежний не годился и что построено взамен

### 1.1. Мина, которой не было в constantinople

Constantinople-заход и стадия 1 мерили приток как **остаток**: всё, что пробник умеет оценить снаружи, вычиталось из наблюдаемого изменения `ep`, а разница называлась боем. Это корректно ровно там, где наблюдаемое изменение информативно — на тиках, где ни один конец шага не упирается в кламп. В `constantinople_1430` таких тиков рабочая доля. В `milan_1477` их **`3.4 %`**: каждый актор доходит до `external_pressure = 100` между тиком `7` и тиком `18` и там остаётся, то есть `96.6 %` партии наблюдаемое изменение равно `0.0` и не несёт информации о доставленном.

Та же асимметрия ломает **контрфакт**. Тень стадии 1 — `s ← clamp(s + Δ_наблюдённое − Δ_производителя)`. На клампованном тике `Δ_наблюдённое = 0`, а `Δ_производителя > 0`, поэтому тень **падает** на всю номинальную поставку производителя, и ничто не начисляет ей то, что в тот же тик клампом срезали у остальных производителей. За `300` тиков любая такая тень уходит в ноль, и тогда всякая смерть приписывается тому производителю, которого тень убрала.

Это **не** опровержение числа задачи 26 само по себе — в её сценарии тень работала преимущественно на свободных тиках. Это утверждение, что тот же инструмент нельзя навести на milan, не перестроив его. Проверка прямая: тень «без миграции» стадии 1 даёт у гибнущих milan-акторов `ep_no_mig = 0.0…19.5` при реальном `100.0` — то есть «весь их `ep` произвела миграция». Номинальная модель на тех же прогонах даёт у тех же акторов тень **`100.0`**.

### 1.2. Режим `epnominal` — перепись притока вместо остатка

Один новый режим. Прежние, включая `epratchet` стадии 1 и `epvalves` стадии 2, переиспользованы **без единого изменения**: `git diff main -- src/bin/budget_probe.rs | grep -c '^-[^-]'` = **0**. Новый бинарник не заводился.

Каждый писатель `external_pressure` перечислен и оценён в своих единицах, **до клампа**:

| производитель | как оценивается | точность |
|---|---|---|
| `auto_deltas` | `price_ep_auto_deltas` (переиспользована), по предтиковому срезу — так же, как их читает фаза 1 | детерминированная часть точно, шум — границей |
| **теги актора** | `apply_actor_tags` переприменяет `metrics_modifier` **каждый тик**; набор тегов читается **из мира** каждый тик, потому что два из трёх заразны | точно, вилка pre/post из-за распространения внутри тика |
| патронские действия | из записей `player_action_*`, которые пишет `apply_player_action`, и из эффектов самого действия | **номинально**, а не по доставленному — иначе четыре отрицательных `ep`-эффекта milan считались бы по тому, что пропустил потолок |
| случайные события | `event_writes_to` (переиспользована) | точно |
| миграция | **реплицируется**, а не решается по населению (§1.3) | оценка + верхняя граница |
| бой | `should_record_event` для `Military` возвращает `true` **безусловно** (`interactions.rs:1067`), поэтому каждый бой оставляет запись `military_conflict_<att>_<def>` | **счёт точный**, масса в вилке `[15n, 25n]` |
| наследование | преемник рождается с `ep_родителя × 1.3`; входит как стартовое значение своей тени, а не как приток | точно |

Всё, что ниже, — **вилка**, и именно это делает перепись проверяемой, а не заявленной.

### 1.3. Почему миграция реплицируется, а не решается

`solve_migration_v2` определяет набор сработавших источников, подгоняя предсказанное **население** под то, которое дал тик. Для объекта задачи 26 это верный инструмент, здесь — неверный: в `milan_1477` он оставляет `6…11` тиков за партию нерешёнными, и, что хуже, подмножество, сходящееся по населению в пределах допуска, не обязано быть подмножеством, двигавшим давление.

Давление не решается — оно **реплицируется**: гейт (`ep > 65 ∧ cohesion < 40`), тай-брейк (`actor_a` первым), агрегация по источнику и попарный `(ep − 65)·0.2/distance` детерминированы при известном состоянии. Чего реплика снаружи не видит — **когда именно** внутри фазы 3 доходит очередь до конкретной пары: пары обрабатываются последовательно, каждая сначала считает бой, поэтому давление источника и когезия кандидата могут сдвинуться между началом тика и моментом его пары. Отсюда три числа на приёмник, а не одно: оценка по состоянию после фазы 1 и вилка, достаточно широкая, чтобы вместить любой порядок — «мог быть источником» судится по **наименьшей** когезии, через которую актор мог пройти (защитник теряет `10…20` за бой), а не по любому из концов. Именно так `ostrogoths` в rome становятся источником незаметно.

### 1.4. Конвейер тика, а не сумма

Наивная модель `clamp(prev + Σ)` точна лишь пока все производители положительны, потому что `clamp(clamp(x) + y) = clamp(x + y)` требует `y ≥ 0`. `milan_1477` этому удовлетворяет (все четыре его `ep`-блока с положительной базой, отрицательных нет), `constantinople_1430` — нет: три блока `byzantium` дают `−2.675` за тик, применение фазы 1 обрезает это о нижний кламп (`MetricRef::apply` клампит на каждом применении), и `+1` от `crusade_caller` ложится уже на пол, а не на арифметическую сумму. Его давление стоит ровно на `1.000` сто тиков подряд — число, которое сумма получить не может.

Поэтому конвейер проходится по фазам: патронские действия (до фазы 1, кламп на каждом эффекте) → `auto_deltas` (фаза 1, кламп на каждом блоке) → бой и миграция (фаза 3, без клампа) → случайные события (фаза 3b, кламп на каждом эффекте) → теги (фаза 4) → фаза 5.

### 1.5. Самотесты — три, и все обязательные

| самотест | что доказывает | результат на 90 партиях |
|---|---|---|
| пошаговый: `ep(t) ∈ [шаг(ep(t−1), lo), шаг(ep(t−1), hi)]` | **перепись полна** — производитель, которого в ней нет, проявляется здесь как нарушение; пройти этот тест с неполным списком нельзя | **`1`** нарушение из ≈ `314 026` актор-тиков (`3·10⁻⁶`) |
| накопительный: тень `IDENT` (ничего не убрано), ведомая от первого тика актора, обязана держать реальное значение между своими ветвями | перепись полна **на траектории**, а не только пошагово | **`0`** |
| реплика движкового `collapse_warning_ticks` | вердикт смертности воспроизведён | **`0`** расхождений |
| разбор пар боя однозначен | счёт боёв не угадан | **`0`** неоднозначных |
| база смертности воспроизведена | инструмент мерит ту систему | **`254 / 120 / 109 / 25`** — точно ратифицированная база §8.6 |

Единственное нарушение — `byzantium`, `constantinople_1430/balanced`, сид `7`, тик `99`, `+0.35` сверх верхней границы. Класс известен и назван constantinople-заходом (§14.3, там он сводился к `±0.02`): фаза 1 идёт по списку `auto_deltas` по порядку, и блок, пишущий **другую** метрику, может сдвинуть величину, которую читает более поздний `ep`-блок; `constantinople_1430` оценивает три блока `byzantium` против `ottomans.military_size`, который более ранний блок уже изменил. Оценка по предтиковому состоянию — конец вилки, а не значение; второй конец — та же оценка на состоянии конца тика, и они вилкой накрывают то, что фаза 1 начислила. В `milan_1477` совпадают для трёх блоков из четырёх (единственное исключение — `#2`, читающий `milan.legitimacy`, который пишет `#0`), и **milan даёт `0` нарушений в `20` партиях из `20`**.

Последняя строка — не совпадение и не свойство RNG. `MILAN_AGGRESSIVE` — единственная сценарная стратегия проекта для milan — ставит `call_papal_arbitration` и `milan_savoy_alliance` **тринадцатым и четырнадцатым** из четырнадцати, при `actions_per_tick = 3` и правиле «останавливаться, как только казны меньше порога плюс стоимость». Это тот же класс, что дефект формы §14.4 constantinople-захода («клапан поставлен и не открывается»), но по другой причине: там условие недостижимо по построению, здесь **порядок приоритетов** делает действие недостижимым.

Тени меняют `ep` и пересчитывают вердикт смертности. Они **не** моделируют того, что изменившийся `ep` сделает через пять зависимостей, читающих его у каждого актора. Эта величина посчитана отдельно, в её собственных единицах — сумма за партию по всем живым акторам milan:

| второй порядок предсказуем по знаку | **нет:** `+8 874` когезии за партию висит на потолке `ep` (§6.1) | — |

**`(C)` принимается**, и в формулировке, которой у constantinople не было: **храповик `external_pressure` в milan не имеет единственного производителя.** Метрика насыщается к тику `7.5…17.7` четырьмя независимыми каналами, каждый из которых почти самодостаточен; два самых крупных — движковые (`71 %` теги, `6 %` бой) и исключены из объёма явно; третий (`18 %` миграция) — объект только что откалиброванной задачи 26 и по измерению не решает ни одной смерти; четвёртый (`4 %` `auto_deltas`) — единственный, помещающийся в один файл контента, и по измерению не решает ничего.

**Чего `(C)` здесь НЕ означает.**
- Не означает, что производители исправны: тег-канал — дефект формы, назван в §9 п.2, и он объективен.
- Не означает, что задача 27 закрыта: остаётся заход `(B)` для **rome** (`57` смертей `conquest`), и его картину этот заход изменил — там тег-канал `93 %` притока, а бой один достаточен для всех `57` смертей.
- Не означает, что `(A)` подтверждён или опровергнут: §5.3 фиксирует расхождение с числом, на котором его отклонили, и передаёт решение постановщику.

## 9. Что требуется от постановщика

1. **Решить, что делать с расхождением по `(A)`.** Свип затухания на номинальной модели не воспроизводит отклик, на котором `(A)` был отклонён (`λ ≤ 2` → `0` снятых во всех девяти конфигурациях; `λ = 4` → `conquest` `120 → 54`, критерий пройден; `λ = 8` → `1`). Расхождение относится к **инструменту**, а не к milan, поэтому оно касается и решения §13.1 по constantinople. Заход его не переоткрывал.
2. **Решить, что делать с найденным `(D)` — потиковым переприменением `metrics_modifier`.** Это крупнейший производитель `external_pressure` в **трёх** сценариях (`59…93 %`) и класс «дефект формы», а не баланса: поле называется `metrics_modifier`, имеет тип `i32` и значения `1, 2, −1, −2`, то есть читается как статический модификатор («у этого актора экономика на 2 выше, потому что он банковская республика»), а `apply_actor_tags` (`mod.rs:684`) начисляет его **каждый тик**, превращая `+2` в `+600` за партию.

   **И проект уже ратифицировал ровно этот инвариант — с неполным списком метрик.** `tests/scenario_conventions.rs::tags_touching_guarded_metrics_do_not_spread` требует `spread_chance = 0.0` от любого тега, пишущего «охраняемую» метрику, и его собственный докстринг называет механизм дословно: «Cultural/trade/war contagion across a dense neighbor graph stacks these modifiers on every actor within a few dozen ticks, saturating the metric at its clamp — this is exactly what made the vassalage band unreachable in Milan 1477». `GUARDED_METRICS = ["legitimacy", "cohesion"]`. Список клампа `0..100` в `mod.rs:707` — **пять** метрик: `legitimacy`, `cohesion`, `military_quality`, `economic_output`, **`external_pressure`**. Три из пяти оставлены без охраны, и у всех трёх заразных тегов много: по `external_pressure` — **9** (constantinople `crusade_caller`, `ottoman_frontier`; milan `ottoman_frontier +2`, `french_orbit`; rome `migrating`, `rhine_border`, `roman_frontier`, `persian_border`, `roman_border`), по `military_quality` — **13**, по `economic_output` — **19**. Всего **41** пара «заразный тег × клампованная неохраняемая метрика» в трёх сценариях.

   **Правка не написана намеренно, и на числах:** она снимает `0` смертей из `254` (§5.2), то есть по стандарту §14.15 п.1 constantinople-захода не имеет измеримого показателя, который бы её оправдал внутри этого захода; она затрагивает контент **трёх** сценариев и делает критерий «rome и constantinople байт-в-байт» недостижимым; и она забирает `+8 874…+9 213` когезии за партию только в milan (§6.1), то есть по последствиям это правка по когезии, а её знак расчёт предсказать не может. Пункт заводится отдельно, со своим объёмом и своими критериями.
3. **Принять к сведению, что ратифицированный критерий `conquest ≥ 42` инертен и в milan.** Constantinople-заход записал обратное («для milan (`46`) и rome (`57`) он различает»); измерение показывает, что ни один кандидат `(B)`, включая тройной, не опускает `conquest` ниже `109` из `120`. Критерий продолжает работать против `(A)` при `λ ≥ 8` и ни против чего другого.
4. **Принять к сведению три меньших дефекта формы, найденных обходом** (§10).
5. **Решить, идти ли в заход `(B)` для rome** — и с какой посылкой: этот заход её изменил (тег-канал `93 %` притока rome; бой один достаточен для всех `57` смертей `conquest`; миграция — `2.3…2.9 %`).

## 14. Воспроизведение

```bash
SEEDS=42,1,7,13,99,3,21,55,77,88

# перепись притока, тени производителей, свип λ, потребители — девять конфигураций
for sc in milan_1477 constantinople_1430 rome_375; do
  cargo run --release --bin budget_probe -- epnominal $sc 300 $SEEDS noplayer; done
cargo run --release --bin budget_probe -- epnominal milan_1477 300 $SEEDS aggressive
for st in balanced military diplomacy; do
  cargo run --release --bin budget_probe -- epnominal constantinople_1430 300 $SEEDS $st; done
for st in balanced wealth; do
  cargo run --release --bin budget_probe -- epnominal rome_375 300 $SEEDS $st; done

# охраняемая база §11
for st in balanced military diplomacy; do
  cargo run --release --bin budget_probe -- attractor constantinople_1430 300 $SEEDS $st; done
cargo run --release --bin budget_probe -- attractor milan_1477 300 $SEEDS aggressive
cargo run --release --bin budget_probe -- attractor rome_375 300 $SEEDS balanced

# обход контейнеров (§2)
cargo run --release --bin budget_probe -- inventory external_pressure
```

Решающие строки: `#EPN` — итог партии, включая все самотесты, разложение притока и свип `λ`; строки без префикса — по актору: занятость, `drops`, номинал каждого производителя, масса, выброшенная клампом; `#TAG` — носители каждого `ep`-тега, тик получения и масса; `#DEATHM` — каждая смерть с путём, вердиктом каждой тени (вилка `[lo|mid|hi]`) и вердиктом каждого `λ`; `#CONS` — занятость каждого условия, читающего `ep`, найденного обходом; `#DEP` — масса пяти зависимостей; `#VIOL`/`#VIOLEV` печатаются **только при нарушении** пошагового самотеста и несут разложение и список событий тика.
